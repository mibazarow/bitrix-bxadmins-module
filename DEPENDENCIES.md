# Зависимости модуля на чистом сервере

Область: собственный сервер/VPS с чистым 1С-Битрикс, есть root/sudo. Shared-хостинг
не рассматриваем. Ниже — всё, что нужно докрутить, чтобы модуль работал полноценно,
что произойдёт без каждой зависимости и что из этого можно автоматизировать.

## Короткий ответ

На чистом Битриксе модуль **установится**, но полноценно не заработает без:

1. **PHP 8.1+** с набором расширений и разрешёнными `proc_open`/`exec`;
2. **Node.js 18+** — без него не работает демон, то есть агент вообще ничего не выполняет;
3. **cron Битрикса** — без него не идёт индексация, не стартует демон, не работают расписания;
4. **MySQL-клиента** (`mysqldump`, `mysql`) и **git** — без них нет бэкапов и полного отката;
5. **сервиса эмбеддингов** (`127.0.0.1:8000`) — без него поиск деградирует до FULLTEXT;
6. **headless Chrome** — без него нет браузерных инструментов;
7. **исходящего HTTPS** и **правильных часов** (NTP) — иначе не будет ни модели, ни HMAC-подписи демона;
8. **LLM-подключения** (endpoint + ключ + модель с tool calling).

Доставка событий в браузер больше не требует Push&Pull: она встроена в модуль
(SSE + журнал событий в БД) и не добавляет серверных зависимостей. **BxMCP** и
**Scrapling** — опциональны, в поставку файлами не входят.

На чистом сервере остаётся **шесть внешних компонентов**: Node, Chrome, сервис
эмбеддингов, MySQL-клиент, git и cron. Именно они, а не MCP, определяют «просто так
заработает или нет».

Для автоматизации есть `environment/install.sh`: на Debian/Ubuntu и RHEL-совместимых
он проверяет и доустанавливает системные пакеты (включая `git`, mysql-клиент, cron,
библиотеки Chrome), ставит Node, BxMCP, EmbeddingGemma 2, Scrapling и Chrome из сети
(или из `--payload` для офлайна), настраивает systemd/cron. Индекс BxMCP строится
на месте, а не поставляется готовым.

## 2. Подробно по каждой группе

### 2.1. PHP

Минимум — 8.1, проверено до 8.5. Обязательные расширения:

```
pdo_mysql  curl  mbstring  json  xml  openssl  zip  fileinfo
```

Зачем:

- `zip` — SQL-дампы (`BackupService`), чтение `.docx`/`.xlsx` во вложениях;
- `fileinfo` — определение MIME вложений (`AttachmentService::mime()`);
- `openssl` — HTTPS, S3-подпись, разбор TLS-сертификата в статусе сервера;
- `curl` — HTTP-клиент Битрикса (LLM, MCP, MCP-скрапер, S3);
- `mbstring` — весь текст и обрезки.

Дополнительно:

- `Imagick` — сильное улучшение для картинок и PDF, но не обязателен: есть fallback;
- **PDF через Imagick требует Ghostscript** и разрешающего `policy.xml`; без этого PDF-вложения не читаются;
- `gd` не обязателен, но часто уже стоит в Битриксе.

Критично: в `disable_functions` **не должно быть** `proc_open`, `exec`, `shell_exec`.
Иначе демон не запустится, бэкапы и git-откат не будут работать, а `run_php`/`write_*`
потеряют проверку синтаксиса.

Лимиты, которые надо поднять вручную:

```
upload_max_filesize = 32M
post_max_size = 32M
memory_limit = 256M+   (индексация, PDF, большие страницы)
max_execution_time = 60+ для админских запросов
```

### 2.2. MySQL / MariaDB

- Пользователь БД должен уметь `CREATE`, `ALTER`, `DROP`, `INDEX` — иначе установка
  не создаст 14 таблиц, а обновление модуля не добавит новые.
- Нужен `utf8mb4` и InnoDB.
- Нужен `FULLTEXT`-индекс (`b_mibazarow_bxadmins_index`) — это резервный поиск,
  если сервиса эмбеддингов нет.
- Для `mysqldump --routines --events` нужны права на чтение процедур/событий
  (в MariaDB/MySQL права различаются); урезанный пользователь может уронить бэкап.
- Для восстановления — право импорта с `DROP`/`CREATE`, иначе `mysql < dump.sql` упадёт.
- Часовой пояс MySQL и PHP должен совпадать, иначе расписания и `CREATED_AT` «плывут».

### 2.3. Файловая система и права

Пользователь PHP (обычно `bitrix`) должен писать:

| Путь | Что там |
|---|---|
| `<site>/local/` | правки шаблонов, компонентов, модулей |
| `<site>/` | `robots.txt`, `urlrewrite.php`, статические страницы |
| `<site>/upload/bxadmins/` | картинки и документы из чата |
| `<site>/bitrix/admin/` | установка/удаление admin-обёрток |
| `<site>/bitrix/backup/bx_admin_s_bacaps/` | SQL-дампы и снапшоты файлов |
| `<site>/bitrix/managed_cache/` | сброс кеша |
| `<site>/../bxadmins-data/` | логи, скриншоты, git, файлы чата |

Важно: `bxadmins-data` вычисляется как «каталог выше docroot» + `/bxadmins-data`
(`Config::logDir()`, `GitService::dataDir()`, `AttachmentService::dir()`).
Если раскладка нестандартная, путь задаётся опцией `log_dir`, но git/вложения всё равно
смотрят в `dirname(dirname(docroot))` — это надо помнить при нестандартном деплое.

**Безопасность nginx:** дампы лежат внутри `bitrix/backup/`, а модуль кладёт туда
`.htaccess`. Apache его читает, **чистый nginx — нет**. На nginx обязательно закрыть
`/bitrix/backup/` в конфиге, иначе SQL-дампы могут скачаться по HTTP. Это надо либо
добавить в setup, либо перенести бэкапы в `bxadmins-data` (правильнее).

### 2.4. Cron и агенты

Модуль регистрирует 5 агентов:

| Агент | Интервал | Что делает |
|---|---|---|
| `IndexAgent` | 15 мин | двигает индексацию батчами |
| `MaintenanceAgent` | сутки | чистит БД, логи, скриншоты |
| `DaemonAgent` | 60 с | поднимает Node-демон, если упал |
| `ScheduleAgent` | 60 с | запускает задачи по расписанию |
| `ScraperAgent` | 60 с | поднимает Scrapling, если он настроен |

Без cron:

- индекс никогда не завершится, а чат заблокирован до `index_complete=Y`;
- демон может не запуститься (если не было ни одного хита админки);
- расписания не срабатывают;
- упавший демон не поднимется.

Требование: `/etc/cron.d/bitrix-cron` каждую минуту от пользователя сайта. Проверка:
`SELECT NAME, LAST_EXEC FROM b_agent WHERE MODULE_ID='mibazarow.bxadmins'` — пять строк
с непустым `LAST_EXEC`.

### 2.5. Node.js и демон

- Node 18+, проверено на 22. Внешних npm-зависимостей нет — только стандартная библиотека.
- Node должен быть виден из cron (`command -v node`), иначе `DaemonAgent` напишет
  «node не найден в PATH». nvm/asdf из cron обычно не видны — нужен симлинк в `/usr/local/bin`.
- Демон слушает `127.0.0.1:8899` (внутренний API браузера). Порт должен быть свободен
  и не открыт наружу.
- Один экземпляр защищён PID-файлом `daemon/.daemon.lock`; каталог модуля должен быть
  доступен на запись пользователю PHP.
- Демон ходит на `127.0.0.1` с `Host` нужного сайта: это требует, чтобы локальный
  веб-сервер отвечал на этот `Host` (виртуальный хост настроен).
- `SITE_URL` берётся из `daemon_site_url`; на мультисайте админка должна быть открыта
  хотя бы раз, чтобы опция записалась.

### 2.6. Headless Chrome

- `chrome-headless-shell` (chrome-for-testing) в `bxadmins-data/chrome` или системный
  Chromium через `CHROME_BIN`.
- Системные библиотеки: `libnss3`, `libatk-bridge2.0-0`, `libcups2`, `libdrm2`,
  `libgbm1`, `libasound2`, `libxkbcommon0`, `libxcomposite1`, `libxdamage1`, `libxrandr2`.
  Либо положить их в `bxadmins-data/chrome/libs` и выставить `LD_LIBRARY_PATH`.
- Без Chrome работают все инструменты, кроме `browser_*`; проверка дизайна — только DOM/CSS.

### 2.7. Сервис эмбеддингов

Самый незаметный, но важный компонент. Это **не часть Битрикса**:

```
POST http://127.0.0.1:8000/embed
{"text": "...", "profile": "site_passage" | "site_query"}
→ {"embedding": [...], "dim": 256, "model": "..."}
```

- Нужен Python/FastAPI-сервис с моделью `google/embeddinggemma-2` (на текущем сервере —
  systemd-юнит `bxmcp-embeddings.service`).
- Модель обрезает вход до 512 токенов, поэтому индекс режется на ~1500 символов.
- Сервис слабый по CPU: ~3–5 с на фрагмент; полная индексация — десятки минут.
- Без сервиса `RagService` уходит в MySQL FULLTEXT/LIKE: работает, но качество семантики ниже.

Этот же сервис использует BxMCP для поиска по документации — то есть при наличии
BxMCP зависимость уже стоит.

### 2.8. CLI-утилиты

| Бинарник | Где используется | Без него |
|---|---|---|
| `node` | демон | агент не выполняет задачи |
| `chrome-headless-shell` | браузерные инструменты | нет browser_* |
| `mysqldump` | бэкапы | нет дампов |
| `mysql` | восстановление | нет отката БД |
| `git` | полный откат сайта | нет `restore_site` и откатов разрушительных операций |
| `diff` | diff в карточке | упрощённый встроенный diff |
| `setsid` | запуск демона/скрапера | процессы могут умирать с запросом |
| `ps` | сторож процессов | дубли демона/скрапера |
| `python3`, `pip`, `venv` | Scrapling | скрапер недоступен |
| `scrapling-mcp` | Scrapling | скрапер недоступен |
| `PHP_BINARY` | `run_php`, `php -l` | часть инструментов не работает |

Все бинарники ищутся через `PATH` и типовые каталоги (`BinaryFinder`), поэтому cron
должен иметь тот же `PATH`, что и shell. Это частая причина «в терминале есть, из модуля нет».

### 2.9. Сеть, порты, время

Исходящий HTTPS нужен:

- к LLM-провайдеру (основная работа);
- к MCP-серверам (если подключены);
- к S3 (если настроено);
- к Openverse/Wikimedia (`search_images`);
- к серверу обновлений Битрикса (скачивание модулей);
- к PyPI и storage.googleapis.com (установка Scrapling/Chrome, если автоматизировать).

Внутренние порты (наружу не открывать):

| Порт | Кто |
|---|---|
| 8899 | демон, browser API |
| 8000 | сервис эмбеддингов |
| 3100 | BxMCP (опционально) |
| 3101 | Scrapling (опционально) |

Наружу — только 80/443.

**NTP обязателен:** HMAC демона проверяет `abs(time() - timestamp) > 120` и отклоняет запрос.
Сбитые часы = «задачи не выполняются» без внятной причины. Проверка: `timedatectl` /
`chronyc tracking`.

### 2.10. LLM

- endpoint, API-ключ, модель — хранятся в `b_mibazarow_bxadmins_llm_profile`;
- модель обязана поддерживать **tool calling**, иначе агент не сможет управлять сайтом;
- для картинок нужна vision-модель (иначе изображения не анализируются);
- контекстное окно задаётся на профиль (по умолчанию 240 000) и влияет на компактацию;
- таймаут 60 с на ответ; провайдер должен отдавать `text/event-stream` для стриминга
  (без него ответ приходит целиком — работает, но без «печати»).

### 2.11. Доставка событий (SSE)

Своя, встроенная: демон пишет события в `b_mibazarow_bxadmins_task_event`,
браузер читает их через `admin/stream.php`. Не нужны ни `pull`, ни `push-server`,
ни `/rest/`, ни дополнительные порты или пакеты.

### 2.12. MCP-серверы

Кратко:

- **BxMCP** — Node-сервис (≈84 МБ зависимостей) + SQLite-индекс, порт 3100.
  В `environment/` входят код сервера и документация (≈22 МБ); индекс строится
  на месте. Подключается как обычный MCP-сервер. Даёт код ядра, поиск
  функций/классов и документацию.
- **Scrapling** — Python/venv/Chromium ~399 МБ, порт 3101, streamable-http.
  Можно ставить автоматически на VPS; без него работает встроенный Chrome.
- Оба — **не обязательны** для базовой работы модуля. Без BxMCP встроенный поиск
  работает по индексу сайта, но не по коду ядра и документации.

## 3. Что реально не даст «просто так» заработать

По убыванию вероятности:

1. **Нет cron Битрикса.** Индекс не завершается → чат навсегда на экране онбординга.
   Демон и расписания тоже мертвы.
2. **Node не виден из cron** (nvm/asdf) или не установлен. Задачи принимаются и висят.
3. **`proc_open`/`exec` в `disable_functions`.** Демон не стартует, бэкапы и git-откат
   не работают, `run_php` не проверяет код.
4. **Нет сервиса эмбеддингов.** Индекс строится медленно и ищет по FULLTEXT; владелец
   видит «предупреждение», но качество заметно ниже.
5. **Нет `mysqldump`/`mysql`.** Нет бэкапов и отката БД; разрушительные операции опасны.
6. **Нет `git`.** Точечные откаты работают, полный `restore_site` — нет.
7. **Нет Chrome.** Нет скриншотов, DOM/CSS-проверок, дымовых тестов.
8. **Сбитые часы (>2 мин).** HMAC демона отклоняет все запросы: «ничего не происходит».
9. **Права на `bitrix/admin` или `bitrix/backup`.** Установка падает или бэкапы не пишутся.
10. **Нестандартный `bxadmins-data`.** Логи и вложения могут работать, а git — нет:
    путь захардкожен как `dirname(dirname(docroot))`.
11. **Nginx не закрывает `/bitrix/backup/`.** SQL-дампы доступны по HTTP — это уже инцидент.
12. **Лимиты PHP 2–8 МБ.** Вложения до 25 МБ и PDF не загружаются.
13. **Нет NTP.** Плавает время, ломается подпись, съезжают расписания и даты.
14. **Пользователь БД без DDL.** Установка не создаёт таблицы.
15. **Нет исходящего HTTPS/CA.** LLM, MCP и S3 недоступны.
16. **LLM без tool calling.** Чат отвечает текстом, но ничего не меняет на сайте.

## 5. Что стоит доработать в модуле

1. **Страница «Проверка окружения»** (или расширить «Управление»): сейчас карточки
   показывают LLM, индекс, SSE, демон и таблицы. Нет проверок Node, Chrome,
   `mysqldump`, `mysql`, `git`, `proc_open`, прав, эмбеддингов, NTP, cron.
   Это самый дешёвый способ снизить поддержку.
2. **`setup.sh` / `bxadmins doctor`** — один скрипт, который проверяет всё из §4 и
   печатает «чего не хватает» с командами установки.
3. **Автоустановка Chrome** — скачивание chrome-for-testing в `bxadmins-data/chrome`
   по кнопке (curl + unzip), как уже сделано для Scrapling-агента.
4. **Автоустановка Scrapling** — установщик в `bxadmins-data` и авторегистрация MCP-сервера.
5. **Единый `can()`-слой** для внешних возможностей: `canBrowser()`, `canBackup()`,
   `canGit()`, `canEmbeddings()`, `canScraper()`. Инструменты должны не падать,
   а объяснять, чего не хватает и как поставить.
6. **Перенести бэкапы из `bitrix/backup` в `bxadmins-data`** — тогда не нужны
   ни `.htaccess`, ни особые правила nginx, и дампы гарантированно вне docroot.
7. **Обновления схемы БД.** Сейчас `install.sql` выполняется только если не хватает
   хотя бы одной таблицы. Изменения в существующих таблицах при обновлении модуля
   не применяются — нужен механизм миграций или явная проверка колонок.
8. **Проверка `PATH` из cron** — показывать в админке, что видит cron, а не shell.
9. **Держать документацию в соответствии:** `setup.md` уже описывает SSE вместо Pull.

## 6. Итог

На чистом сервере модуль требует не «ещё пару MCP», а **инфраструктуру вокруг PHP**:
Node, Chrome, сервис эмбеддингов, MySQL-клиент, git, cron, права и сеть. Из перечисленного
BxMCP и Scrapling — опции, а не фундамент; доставка событий встроена и серверных
зависимостей не добавляет. Всё остальное (Node, Chrome, эмбеддинги, CLI-утилиты) нужно либо
ставить на сервер, либо явно объявлять «без этого функция недоступна» — но модуль не должен
молча ломаться. Сейчас он частично это делает, но диагностика покрывает далеко не все
зависимости из §3.
